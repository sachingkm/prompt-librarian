Prompt Librarian — Design Notes

Local-first desktop app for capturing, classifying, and reusing prompts as Markdown files. Phase 1 = Electron + React + TypeScript. Public, downloadable from GitHub. No cloud, no login, no plugins.

1. Product direction

Quiet, serious, utility-first. Looks and behaves like a text editor or IDE, not a marketing page. Three-pane shell — folder tree on the left, list/editor in the center, metadata on the right — with a status bar pinned to the bottom and a minimal title bar on top. Dense, monospace-accented, keyboard-first.

Default to dark; light theme available. Single curated accent color (blue, amber, violet, or green). No gradients, no marketing iconography, no emoji.

The app is a thin layer over a folder of .md files. The user can leave at any time — Obsidian, VS Code, plain Finder — and the data is intact. That promise is the product.

2. Locked rules

Rule 1. Local Markdown files are the source of truth. The app reads from disk, watches for changes, and writes back. There is no database. Any cache (search index, classifier output) can be rebuilt from the files.
Rule 2. The user must explicitly choose the writable root folder. The app never picks one for them, never assumes a personal path (no Google Drive, no C:\Users\<name> defaults), and never writes outside that folder.
Hard constraints. Never organize prompts by LLM vendor. Never create _gpt / _cld / _ag file variants. Model-specific behavior lives inside a ## Compatibility Notes section in the same prompt file. Folder placement is decided by function → domain → project, in that order.

3. User flow

3.1 First-run (one time per machine)

  1. App launches with no library. Welcome card explains: Markdown on disk, you choose the folder, no cloud.
  2. User picks Create new library or Use existing library.
  3. User selects a folder via OS file picker. App validates write permission.
  4. If Create new: app offers to initialize the default folder structure. Checkbox; can be turned off.
  5. Confirmation screen lists exactly what the app will read, write, watch, and never touch. User clicks Open library.

3.2 Steady-state daily flow

  1. Ctrl+N from anywhere → intake. Paste raw prompt → Classify → review classifier output → Save.
  2. Or: from the system tray, hit the global hotkey Ctrl+Shift+N → tray quick-capture window pops up; paste; send to library; intake opens with text pre-filled.
  3. Ctrl+K command palette for navigation, search, and commands.
  4. Browse the tree, open a file, edit, Ctrl+S to save. File watcher keeps in sync if you edit it externally.
  5. Hygiene tab surfaces under-tagged or untriaged captures.

5. Key screens

1. First-run setup

4-step modal. Welcome → choose new/existing → pick folder → confirm. Always shows what the app will read/write/never touch.

2. Library browser

Three-pane: folder tree, table of prompts (Title, Folder, Function, Reuse, Used, Updated), metadata side panel.

3. Intake / classify

Two-step. Paste box → Classify → review screen with editable left (body) and right (metadata) plus rationale and confidence.

4. Detail / editor

Editor / Preview / Raw Markdown tabs. Same metadata panel on the right. Save with Ctrl+S; close with Esc.

5. Search / command palette

Global Ctrl+K palette: prompts and commands in one list, keyboard navigable.

6. Folder management

Modal lists every folder, prompt count, inline rename, delete (with confirmation that lists affected files).

7. Archive / hygiene

Hygiene flags prompts missing metadata or filed poorly. Archive view shows everything under 99-Archive/; archived files are still searchable but de-prioritized.

+ Tray quick-capture

Tiny window, single textarea. Send to library; main app opens at intake review.

6. Interaction details

Classify

  1. User pastes text and presses Classify (or Ctrl+Enter).
  2. App calls the classifier with a strict JSON-output system prompt. Returned fields: title, function, category, subcategory, domain, project, tags, reuse, scope, folder, filename, confidence, rationale.
  3. If the classifier is unavailable or returns invalid JSON, the app falls back to a local heuristic and stamps the result with heuristic fallback.
  4. Confidence is shown as a small bar with a percentage. ≥75% green, ≥50% amber, <50% red.
  5. The user can edit every field. Re-classify re-runs with the same body. Save writes only after confirmation.

Save

  1. Compose the file: serialize frontmatter + body. Validate filename ends in .md and matches ^[a-z0-9._-]+$ (warn if not).
  2. Ensure the target folder exists; create it (and any missing intermediates) under the library root only.
  3. Atomic write: write to <target>.tmp, fsync, rename. Never overwrite via direct write.
  4. If a file at the target path already exists with different content → open the conflict modal (see §8).
  5. On success, update the in-memory index, post a toast, and reset the intake.

Edit

  • Editor / Preview / Raw Markdown tabs share the same model. Raw view shows the exact bytes that will be written.
  • Auto-save on blur is off by default. Save is explicit. The dirty state shows in the title bar (● filename.md).
  • External edits (file watcher detects mtime change) prompt: keep mine / use disk / open diff. Never silently overwrite either side.

Move

  • Move modal shows the folder tree. Selecting a destination triggers an atomic rename on disk. Updates frontmatter updated_at. The app is the only thing that needs to remember the new path; other notes that referenced it by filename are stable because the slug doesn't change.

Archive

  • "Archive" = move file into 99-Archive/, preserving subfolder structure (99-Archive/03-Job Search/Resume/old.md).
  • Archived files appear in search but with reduced rank; they don't appear in dashboards.
  • "Unarchive" is a Move back to the original folder, available from the metadata panel.

8. Folder choice, collisions, confidence

Folder choice (first-run + later)

  • Always go through the OS file picker. Never type-only.
  • Validate the folder exists, is readable, and is writable before accepting it.
  • Refuse system folders (e.g., root of /, %APPDATA%, the app's own install dir).
  • Persist the choice in the app config file (~/.config/prompt-librarian/config.json or platform equivalent), not in the library itself.
  • Settings → Library → Change root re-runs the same flow.

Collision handling

When a save would write over a different file at the same path, show a modal with three options:

  • Save as new file — auto-suggest name-1.md; user can edit. Default action.
  • Replace existing — destructive, danger button, requires explicit click. Existing version is moved into .trash/ inside the library root, not deleted, for 7 days.
  • Open both side-by-side — opens a diff view so the user can hand-merge into a single file.
Never silently overwrite. Never auto-bump filenames without telling the user. The conflict modal is mandatory.

Confidence display

  • One bar, one number. Color-coded green/amber/red.
  • Always paired with a rationale sentence. The bar without the rationale is meaningless.
  • Below 50%, the Save button stays enabled but the modal copy nudges toward editing first.
  • The classifier never blocks a save. The user is the final word.

9. Engineering handoff (Electron + React + TypeScript)

Stack

LayerChoiceWhy
ShellElectron 30+Cross-platform local desktop, OS file picker, file watcher, system tray, global hotkeys.
RendererReact 18 + TypeScriptStandard, well-supported. Vite for dev.
StateZustand or Redux ToolkitSimple. Don't over-engineer. State is mostly derived from the file index.
File watcherchokidarCross-platform mtime + content events.
Markdown parsinggray-matter + remarkFrontmatter + AST when needed.
Searchminisearch or flexsearch in rendererIn-memory index, rebuilt on boot from files. Cache to .cache/index.json for faster cold starts; checksum-validated.
EditorCodeMirror 6 with Markdown modeLight, scriptable, excellent keyboard support.
Hotkeysmousetrap in renderer; globalShortcut for trayRenderer for in-app, main process for tray quick-capture.

Process boundaries

  • Main process owns: filesystem, file watcher, OS dialogs, global shortcuts, system tray window, app config. Exposes a typed IPC API.
  • Renderer owns: UI, search index, editor state, classifier client. Never touches fs directly.
  • All file operations go through a small fs/ module in main with a root guard: every path is resolved and verified to be inside the library root before any read/write/rename. Out-of-root paths throw.

Key invariants for the build

  1. Root guard. Every fs call validates the resolved absolute path is a descendant of the library root. No exceptions.
  2. Atomic writes. Write to a sibling temp file, fsync, then rename. On rename failure, leave the original intact.
  3. Soft delete. Replace = move existing into <root>/.trash/ with timestamp suffix; cleanup older than 7 days on next boot.
  4. Watcher debounce. 200ms. Multiple events on the same path collapse.
  5. Idempotent reindex. Boot path: read all .md, build index. Any cache must be rebuildable without user data loss.
  6. No vendor coupling. The classifier is a pluggable interface. Default implementation calls Anthropic; a fallback heuristic runs entirely locally. Folder placement is never derived from which model produced a result.

Data layer (TS types)

type FunctionTag =
  | "transform" | "summarize" | "extract" | "classify"
  | "rewrite"   | "compare"   | "generate" | "critique" | "plan";

type Domain =
  | "interview" | "job search" | "product specs" | "research" | "project prompts";

type Reuse = "high" | "medium" | "low";
type Scope = "reusable" | "project reusable" | "one-off";

interface Prompt {
  /* Identity */
  absPath: string;          // //
  folder: string;           // relative to root, forward slashes
  filename: string;         // .md
  /* Frontmatter (all optional in storage; required-ish in UI) */
  title: string;
  category?: string;
  subcategory?: string;
  function?: FunctionTag;
  domain?: Domain | null;
  project?: string | null;
  tags: string[];
  reuse?: Reuse;
  scope?: Scope;
  created_at?: string;      // ISO
  updated_at?: string;      // ISO
  /* Body sections (parsed from Markdown headings) */
  purpose?: string;
  inputs?: string;
  output?: string;
  body: string;             // the actual prompt text (## Prompt section)
  notes?: string;
  compatibility?: string;
}

interface Classification {
  title: string;
  function: FunctionTag;
  category: string;
  subcategory?: string;
  domain?: Domain | null;
  project?: string | null;
  tags: string[];
  reuse: Reuse;
  scope: Scope;
  folder: string;
  filename: string;
  confidence: number;       // 0..1
  rationale: string;
}

interface AppConfig {
  libraryRoot: string;
  watchEnabled: boolean;
  conflictPolicy: "ask" | "rename" | "overwrite";
  defaults: { reuse: Reuse; scope: Scope; filenameFormat: string };
  classifier: { provider: "anthropic" | "heuristic"; apiKeyRef?: string };
  hotkeys: Record<string, string>;
}

Phase 2 portability

If the app later moves to a hosted web app, the model stays:

  • Replace the local fs/ module with a server-backed file API. Frontmatter + folder structure are unchanged.
  • The classifier API is already pluggable.
  • The user still picks a writable root — it just happens to be a remote bucket prefix.
  • No screen, no field, and no folder needs to change.
